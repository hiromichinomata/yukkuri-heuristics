# 第9章 焼きなまし法（Simulated Annealing）

> **到達目標（緑色帯 800〜1199）**: 局所最適から抜け、温度スケジュールと近傍設計を調整してスコアを伸ばせる。

---

## 9.1 局所最適から抜け出す発想

**霊夢**: 第6章の山登り、悪い手は絶対に受け入れないんでしょ？ そしたら谷から出られないのでは？

**魔理沙**: その通りだ。**山登り（Hill Climbing）** は「今より良い解だけ採用」するから、**局所最適**に張り付く。

**霊夢**: 局所最適って？

**魔理沙**: **近傍のどれを試しても改善しない解**のことだ。全体ではもっと良い解があるのに、1歩ずつ変えるだけでは届かない谷に落ちる。

```
        スコア
          ^
          |     *  ← 大域的に良い山頂
          |    / \
          |   /   \
          |  /     \___*___  ← 局所最適（ここから脱出できない）
          | /            \
          +------------------→ 解空間
```

**霊夢**: 焼きなましはどうやって抜けるの？

**魔理沙**: **たまに悪化も受け入れる**。受け入れ確率は **温度 T** で決める。T が高いうちは悪手も通しやすく、冷えるほど山登りに近づく——金属を焼いてゆっくり冷やすイメージだぜ。

| 手法 | 悪化の受理 | 局所最適 |
|------|-----------|----------|
| 山登り | しない | 抜けにくい |
| 焼きなまし | 確率的にする | 抜けやすい |

```python
# 概念: 受理の核心（delta = 新スコア - 今スコア）
import math

def accept(delta: int, temperature: float, rng) -> bool:
    if delta >= 0:
        return True  # 改善は必ず採用
    # 悪化: exp(delta / T) の確率で採用（delta < 0 なので指数 < 1）
    return rng.random() < math.exp(delta / temperature)
```

```go
// 概念: 同じ判定（Go）
func accept(delta float64, temperature float64, rng *rand.Rand) bool {
	if delta >= 0 {
		return true
	}
	return rng.Float64() < math.Exp(delta/temperature)
}
```

**霊夢**: delta がマイナスだと exp は 1 未満になるから、運でたまに通るのね。

**魔理沙**: そう。**T が大きいほど**悪化も通りやすい。**T → 0** に近づくと山登りと同じになる。AHC ではこの「確率的な悪化受理」が緑帯の必須武器だ。

## 9.2 温度スケジュール（初期温度・冷却率・終了条件）

**霊夢**: 温度はどう決めるの？ 適当に下げればいい？

**魔理沙**: 3つセットで決める。**開始温度 T0**、**終了温度 T1**、**終了条件（制限時間）**だ。

| パラメータ | 役割 | 本リポジトリの例 |
|-----------|------|------------------|
| `T0` | 探索初期の「大胆さ」 | テンプレート `100`、第9章本番 `5000` |
| `T1` | 終盤の温度（ほぼ山登り） | テンプレート `0.1`、第9章本番 `10` |
| 終了 | いつ止めるか | **残り時間**（コンテストではこれが正義） |

**霊夢**: T0 がテンプレートと第9章で違うのはなぜ？

**魔理沙**: **スコアのスケール**が違うからだ。`python/templates/sa_template.py` はデモ用に小さな整数、`sa_intro_hc.py` は Intro HC のスコア（百万単位）向けに **T0=5000** にしている。

**霊夢**: 温度はどうやって T0 から T1 まで下げるの？

**魔理沙**: AHC で定番なのは **経過時間の割合で決める** やり方だ。`progress = 経過時間 / 制限時間`（0→1）として、

```text
T = T0 * (T1 / T0) ** progress
```

と置く。progress=0 で T0、progress=1 でちょうど T1。途中は指数的（対数スケールで直線的）に下がる。

```python
# python/templates/sa_template.py — 汎用テンプレ（T0=100 → T1=0.1）
T0 = 100.0
T1 = 0.1

def sa(initial_state, neighbor_fn, score_fn, time_limit_sec=2.0, rng=None):
    # ...
    while True:
        elapsed = time.perf_counter() - start
        if elapsed >= time_limit_sec:
            break
        progress = elapsed / time_limit_sec
        temperature = T0 * (T1 / T0) ** progress
        # ...
        if delta >= 0 or rng.random() < math.exp(delta / temperature):
            state = new_state
            score = new_score
```

```python
# python/ch09/sa_intro_hc.py — Intro HC 向け（T0=5000 → T1=10）
T0 = 5000.0
T1 = 10.0
TIME_LIMIT_SEC = 1.5

# ループ内
progress = elapsed / time_limit_sec
temperature = T0 * (T1 / T0) ** progress
```

```text
# 経過割合と温度（T0=5000, T1=10）
progress=0.00 → T = 5000
progress=0.25 → T ≈ 1057
progress=0.50 → T ≈ 224
progress=0.75 → T ≈ 47
progress=1.00 → T = 10
```

**霊夢**: 1ステップごとに `T *= 0.995` みたいに掛ける方法もあるって聞いたけど？

**魔理沙**: **ステップ数ベースの幾何冷却** `T ← T × ALPHA` だな。書くのは簡単だが、AHC では落とし穴がある。**1秒で何ステップ回るかは問題・言語・マシンで全然違う**から、温度が下がり切るタイミングが読めない。

```text
# T0=5000, ALPHA=0.995 のとき
n=500   → T ≈ 408
n=1000  → T ≈ 33
n=1500  → T ≈ 2.7
n=3000  → T ≈ 0.0015   # 以降はほぼ山登り
```

**魔理沙**: このサンプルだと Python でも 1.5 秒で 50 万ステップ以上回る（9.4 の差分更新込み）。幾何冷却だと**最初の 1% にも満たない時間で冷え切って、残りはただの山登り**になる。時間ベースなら、言語や速度が違っても **制限時間いっぱいまで温度が残る**。だから本リポジトリは時間ベースを採用している。

**霊夢**: 終了条件は「ステップ数」じゃなく時間？

**魔理沙**: AHC では **`time.perf_counter()` と締切** が基本。ステップ上限だけだと、近傍が重い問題で TL を超える。

```python
# 骨格: 時間で打ち切るループ
start = time.perf_counter()
while time.perf_counter() - start < time_limit_sec:
    # 1 iteration
```

**霊夢**: 初期温度の決め方は？

**魔理沙**: 経験則で **「悪化 Δ の典型値を、初期段階で 30〜70% くらいの確率で受理できる T」** を探す。本番では stderr の `T=` と `score=` を見ながら `T0` を振る（9.6 演習）。

## 9.3 近傍設計のコツ（小さく変える / 大きく変える）

**霊夢**: 近傍（Neighborhood）って、第6章と同じ？

**魔理沙**: 同じ概念だ。**今の解から少しだけ変えた解の集合**が近傍。SA ではここから **ランダムに1つ** 引いて試す。

| 近傍の大きさ | 例（Intro HC 日程） | 向いている局面 |
|-------------|---------------------|----------------|
| 小 | 1日だけタイプを変える | 仕上げ・微調整 |
| 中 | 2日スワップ、連続区間を反転 | 中盤の探索 |
| 大 | 全日をランダム再生成 | 初期解が酷いとき（別系統） |

```python
# python/ch09/sa_intro_hc.py — 小さな近傍（「どの日を何に変えるか」だけ返す）
def random_move(state: ScheduleState, rng: random.Random) -> Tuple[int, int]:
    day = rng.randrange(len(state.types))
    new_type = rng.randint(1, 26)
    return day, new_type
```

```go
// go/ch09/sa_intro_hc.go
func randomMove(state ScheduleState, rng *rand.Rand) (int, int) {
	day := rng.Intn(len(state.Types))
	return day, rng.Intn(26) + 1
}
```

**魔理沙**: 解をコピーして返すのではなく、**操作（日, 新タイプ）だけ** を返しているのがポイントだ。これで次の 9.4 の差分更新が使える。

**霊夢**: 小さい近傍だけだと遅くない？

**魔理沙**: 1ステップは速いが、大きな改善には **多ステップ** が要る。だから **温度が高いうち** にたまに悪化して谷を越え、**冷えてから** 小さな近傍で詰める、が典型だ。

**霊夢**: 大きい近傍はいつ使う？

**魔理沙**: **複数の neighbor_fn を混ぜる**（確率 0.9 で1日変更、0.1 でスワップなど）か、**パイプライン**で貪欲→山登り→SA（第11章）に任せる。1ファイルに全部詰めなくてもいい。

```python
# 改変例: 9 割は1日変更、1 割は2日入れ替え
def mixed_move(state, rng):
    if rng.random() < 0.9:
        return ("change", *random_move(state, rng))
    return ("swap", *random_swap(state, rng))  # 2日入れ替え（演習3）
```

## 9.4 状態のコピー vs 差分更新（1日変更の Δ を O(D) で計算する）

**霊夢**: 1回試すたびに、365日分のスコアを全部計算し直すの？ 遅くない？

**魔理沙**: 遅い。全再計算は 1回 **O(26·D)** だ。D=365 なら 1 手で約 1 万回の足し算になる。SA は **手数がそのまま強さ** だから、ここを速くするのが緑色帯の最重要テクだぜ。

| 方式 | 1手のコスト | メリット | デメリット |
|------|-----------|---------|-----------|
| **コピー + 全再計算** | O(26·D) | バグが少ない、読みやすい | 遅い |
| **差分更新** | O(D)（工夫すれば O(log D)） | 同じ時間で何倍も試せる | 実装が難しい、戻し方に注意 |

**霊夢**: 差分ってどう考えるの？

**魔理沙**: 満足度を **タイプごとに分解** する。タイプ t を開いた日を a_1 < … < a_k とすると、間隔 L の区間で減る量は c_t × (0 + 1 + … + (L−1)) = **c_t × L(L−1)/2** だ（最初は 0 日目、最後は D+1 日目を端とみなす）。

```text
タイプ t の減衰 = c_t × Σ L(L−1)/2   （L は開催日の間隔）
```

**魔理沙**: ある日のタイプを a → b に変えても、間隔が変わるのは **タイプ a と b だけ**。残り 24 タイプは計算し直さなくていい。

```python
# python/ch09/sa_intro_hc.py
def type_penalty(problem, types, t):
    total = 0
    prev = 0
    for day, x in enumerate(types, start=1):
        if x == t:
            gap = day - prev
            total += gap * (gap - 1) // 2
            prev = day
    gap = problem.days + 1 - prev
    total += gap * (gap - 1) // 2
    return problem.decay[t - 1] * total


def delta_change(problem, types, day, new_type):
    old_type = types[day]
    if old_type == new_type:
        return 0
    before = type_penalty(problem, types, old_type) + type_penalty(problem, types, new_type)
    types[day] = new_type
    after = type_penalty(problem, types, old_type) + type_penalty(problem, types, new_type)
    types[day] = old_type  # 元に戻す（採用するかは呼び出し側が決める）
    gain = problem.gain[day][new_type - 1] - problem.gain[day][old_type - 1]
    return gain - (after - before)
```

Go 版も同じ形だ。`types[day]` を一時的に書き換えて、すぐ元に戻している。

```go
// go/ch09/sa_intro_hc.go
func typePenalty(problem ProblemInput, types []int, t int) int {
	total, prev := 0, 0
	for i, x := range types {
		if x == t {
			day := i + 1
			gap := day - prev
			total += gap * (gap - 1) / 2
			prev = day
		}
	}
	gap := problem.Days + 1 - prev
	total += gap * (gap - 1) / 2
	return problem.Decay[t-1] * total
}

func deltaChange(problem ProblemInput, types []int, day, newType int) int {
	oldType := types[day]
	if oldType == newType {
		return 0
	}
	before := typePenalty(problem, types, oldType) + typePenalty(problem, types, newType)
	types[day] = newType
	after := typePenalty(problem, types, oldType) + typePenalty(problem, types, newType)
	types[day] = oldType // 元に戻す（採用するかは呼び出し側が決める）
	gain := problem.Gain[day][newType-1] - problem.Gain[day][oldType-1]
	return gain - (after - before)
}
```

```python
# python/ch09/sa_intro_hc.py — SA ループ内: 現在解を直接書き換え、採用したときだけ反映する
day, new_type = random_move(state, rng)
delta = delta_change(problem, state.types, day, new_type)
if delta >= 0 or rng.random() < math.exp(delta / temperature):
    state.types[day] = new_type
    score += delta
```

```go
// go/ch09/sa_intro_hc.go — 同じ考え方
delta := deltaChange(problem, state.Types, day, newType)
if delta >= 0 || rng.Float64() < math.Exp(float64(delta)/temperature) {
	state.Types[day] = newType
	score += delta
}
```

**霊夢**: 差分がもし間違ってたら？

**魔理沙**: **全再計算と突き合わせる** のが鉄則だ。第9章のコードは、ループの最後に `score == raw_score(...)` を assert している。差分更新を書いたら、まずランダムな入力で「差分の積み上げ = 全再計算」を確かめろ。

**霊夢**: スコアの `max(…, 0)` はどうするの？

**魔理沙**: SA の中では **0 で切らない値**（`raw_score` = 10^6 + 満足度）を使う。0 で切ると、悪い初期解ではどの手も Δ=0 に見えて SA が何も学べない。切るのは最後に提出スコアを出すときだけだ。

| D=365 のランダム入力で 1.5 秒（Python） | best score |
|-----------------------------------------|-----------|
| 全再計算 + 0 で切ったスコア | 0（初期解から抜けられない） |
| 差分更新 + 切らないスコア | 約 113 万 |

**魔理沙**: 区間ごとの集合を `bisect` で持てば O(log D) まで落とせる（第14章のデータ構造の考え方）。まずは O(D) で十分だぜ。

**霊夢**: SA では best を別に持ってるのね。

**魔理沙**: 重要だ。**現在解 state** は悪化も含めて動く。**best_state** は歴代最高だけ保存。最終出力は **best** を出す（現在が一時的に悪化していても提出はベスト）。

```python
# python/ch09/sa_intro_hc.py
best_state = ScheduleState(list(state.types))
best_score = score

# ループ内
if score > best_score:
    best_score = score
    best_state = ScheduleState(list(state.types))
```

## 章末まとめ

**霊夢**: 悪化も受け入れるのが焼きなましの肝なのね。

**魔理沙**: まとめだ。

> **第9章まとめ**
>
> - **山登り**は局所最適に張り付く。**SA**は温度付きで悪化も確率的に受理する
> - **温度スケジュール**: `T0`（初期大胆さ）→ `T1`（終盤）を **経過時間の割合** で指数的に下げる。ステップ数ベースの `T *= ALPHA` は速度次第で早く冷え切る
> - 本リポジトリ: テンプレ `T0=100 → T1=0.1`、第9章 `T0=5000 → T1=10`
> - **近傍**は小さく始め、必要なら混ぜる。出力は **best_state** を使う
> - **差分更新**: 1日変更で変わるのは2タイプだけ → Δ を O(D) で計算。全再計算との一致を assert で確かめる
> - ハンズオン: `python/ch09/sa_intro_hc.py` / Intro HC 問題C
