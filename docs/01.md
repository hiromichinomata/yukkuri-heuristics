## 1.1 アルゴリズム部門とヒューリスティック部門の違い

**霊夢**: 魔理沙、ヒューリスティック競プロってアルゴリズム部門と何が違うの？

**魔理沙**: 大きく3つだぜ。**正解の数**、**評価の仕方**、**コンテストの長さ**。

**霊夢**: 正解の数？

**魔理沙**: アルゴリズム部門（ABC / ARC / AGC）では、だいたい**正解が決まっている**問題が多い。出力が合えば AC、合わなければ WA だ。

**霊夢**: ヒューリスティックは？

**魔理沙**: **正解が1つとは限らない**。同じ入力でも、より良い解・より悪い解が存在する。AtCoder Heuristic Contest（AHC）では**スコアの高さ**で順位が決まるんだ。

| 観点 | アルゴリズム部門 | ヒューリスティック部門（AHC） |
|------|-----------------|------------------------------|
| 判定 | AC / WA / TLE | スコア（高いほど良い） |
| 正解 | 基本的に一意 | 最適解は未知のことが多い |
| 目標 | 制約内で正しく解く | 制限時間内により高スコアの解を探す |
| 典型手法 | DP、グラフ、データ構造 | 貪欲、山登り、焼きなまし、ビームサーチ |
| コンテスト時間 | 約2時間 | 短期（数時間）〜 長期（約2週間） |

**霊夢**: つまり「100点満点じゃなくて、800点と1200点が競われる」感じなの？

**魔理沙**: その理解でだいたい合ってる。WA にならない**合法解**を出したうえで、**どれだけスコアを伸ばせるか**が勝負だぜ。

**霊夢**: アルゴで培った力は活きるの？

**魔理沙**: 活きる。**実装力**、**計算量の感覚**、**バグを潰す力**は共通だ。加えて、ヒューリスティックでは次の発想が重要になる。

1. **スコア関数を自分で書く**（後述）
2. **近傍操作** — 解を少し変えて試す
3. **時間を使い切る** — TL 内で探索を続ける
4. **ビジュアライザ** — 目で解を確認する

```python
# アルゴ: 正解判定イメージ
def judge(output, expected):
    return output == expected  # True なら AC
```

```python
# ヒューリスティック: スコア判定イメージ
def judge(output, score_fn):
    if not is_valid(output):
        return "WA"
    return score_fn(output)  # 整数スコア（大きいほど良い）
```

```go
// go/ch01/judge_example.go — 同じ対比（概念デモ）
package main

import "fmt"

func judgeAlgo(output, expected int) string {
	if output == expected {
		return "AC"
	}
	return "WA"
}

func judgeHeuristic(score int, valid bool) any {
	if !valid {
		return "WA"
	}
	return score
}

func main() {
	fmt.Println(judgeAlgo(42, 42))
	fmt.Println(judgeHeuristic(1079325, true))
}
```

**霊夢**: 最初は低いスコアでもいいの？

**魔理沙**: もちろん。**まず合法解**、次に**ちょっとマシな解**、そのあと**焼きなましで伸ばす**——この順番が定番だ。第4章以降で具体的にやるぜ。

## 1.2 AHC のコンテスト形式

**霊夢**: AHC ってどんなコンテストなの？

**魔理沙**: [Heuristic Contest 概要](https://info.atcoder.jp/overview/contest/heuristic) のとおり、**1問出題**が基本だ。Algorithm 部門みたいに A/B/C/D 問題が並ぶ形式じゃない。

**霊夢**: 問題数は1つだけなのね。

**魔理沙**: その分、1問に集中する。**短期**と**長期**があるのが AHC の特徴だ。

| 種類 | 目安 | 特徴 |
|------|------|------|
| 短期 | 数時間（例: 19:00–23:00） | その場の集中力勝負 |
| 長期 | 約2週間 | 平日も改善を重ねられる |

**霊夢**: 提出は何回でもできるの？

**魔理沙**: できる。ただし**同じ問題への提出間隔は5分**空ける必要がある。別問題なら間隔制限はない（Intro HC など複数問題ある場合）。

**霊夢**: ローカルで試すには？

**魔理沙**: だいたいの AHC 問題で、次が配布される。

1. **入力ジェネレータ** — テストケース生成
2. **スコア計算（ジャッジ）** — 出力の点数を計算
3. **ビジュアライザ** — 解を可視化

Rust で書かれた `tools` をコンパイルして使う形式が多い。Intro HC も同じ形式だ。

```bash
# tools の典型構成（AHC / Intro HC 共通イメージ）
tools/
├── Cargo.toml
├── src/
│   ├── bin/
│   │   ├── gen.rs    # 入力生成
│   │   ├── score.rs  # スコア計算
│   │   └── vis.rs    # ビジュアライザ
```

```bash
# ローカル評価の流れ（例）
./tools/gen 0 > input.txt
python python/ch01/solution.py < input.txt > output.txt
./tools/score input.txt output.txt
./tools/vis input.txt output.txt
```

**霊夢**: Python しか書けなくても参加できる？

**魔理沙**: できる。AtCoder 本番提出も Python / Go / C++ など多数対応だ。本書は **Python と Go** で解法を並べる。ローカルの `tools` だけ Rust 環境が必要なことがあるが、**スコア計算は自分で Python / Go に移植** することも多い——第1章のハンズオンがまさにそれだぜ。

**霊夢**: Intro HC って何？

**魔理沙**: [Introduction to Heuristics Contest](https://atcoder.jp/contests/intro-heuristics) のこと。入門者向けで、問題 A のほかに**ガイド付きの B・C** がある。スコア計算から貪欲法まで段階的に学べる。第1章のハンズオンでは、ここの**問題B（Scoring）** を題材にするぜ。

## 1.3 AHC レーティングのしくみ

**霊夢**: ヒューリスティック部門のレートって、アルゴと同じなの？

**魔理沙**: **仕組みが違う**。公式説明は [レーティングのしくみ](https://info.atcoder.jp/overview/contest/rating) を見てくれ。ここでは雰囲気だけ押さえるぜ。

**霊夢**: 負けたら下がる？

**魔理沙**: AHC の Heuristic レートは**単調非減少**——**下がらない**んだ。低いパフォーマンスを出しても、レートが下がったり、将来上がりにくくなったりはしない。

**霊夢**: へえ、参加するほど得なのね。

**魔理沙**: ただし**上がり方**は「平均」じゃなく**ベストパフォーマンス寄り**だ。Kaggle の Master 称号に近いイメージと公式も説明している。良い結果を出したコンテストほど、レート計算に効きやすい。

| 項目 | Algorithm 部門 | Heuristic 部門（AHC） |
|------|---------------|----------------------|
| レート変動 | 上下する | **下がらない** |
| 評価の中心 | 直近平均（古い結果は薄れる） | **良いパフォーマンス**が効く |
| Rated 条件 | Rated 登録で未提出でも対象 | **1回以上提出**が必要 |
| 参加回数 | 少ないと補正で低め | 足りない分を**低めの推定値**で補完 |

**霊夢**: 色の境目は？

**魔理沙**: アルゴと同じ色体系だ。2026年1月時点の目安はこうだ。

| レーティング | 色 | ヒューリスティック部門の人数割合（目安） |
|-------------|-----|----------------------------------------|
| 1–399 | 灰色 | 約 63% |
| 400–799 | 茶色 | 約 11% |
| 800–1199 | 緑色 | 約 10% |
| 1200–1599 | 水色 | 約 8% |
| 1600–1999 | 青色 | 約 4.5% |
| 2000–2399 | 黄色 | 約 2.3% |
| 2400–2799 | 橙色 | 約 0.8% |
| 2800– | 赤色 | 約 0.3% |

**霊夢**: 本書の章もこの色に対応してるのね。

**魔理沙**: そう。第2章以降は灰色帯から順に深くなる。第1章は**全体像**なので色は問わない。

func ratingBand(r int) string {

		limit int

**霊夢**: 参加回数が少ないと不利なの？

**魔理沙**: 実力より**低めに見積もられる**ことがある。だから公式も「失敗してもアカウントを消さず、出続ける方が得」と言っている。焦ってサボるより、**出てスコア計算の経験を積む**方がいいんだ。

## 1.4 スコアリング関数・ビジュアライザ・提出の基本フロー

**霊夢**: スコアリング関数って、問題文に書いてあるやつ？

**魔理沙**: そう。**出力から点数を計算するルール**だ。ヒューリスティックでは、これを**自分のコードにも実装する**のが鉄則だぜ。

**霊夢**: なんで？ 公式ジャッジがあるのに。

**魔理沙**: 理由は3つ。

1. **問題理解の確認** — 仕様をコードに落とせるか
2. **ローカルデバッグ** — 提出前に点数を見られる
3. **解法の部品** — 貪欲や焼きなましの評価にそのまま使える

Intro HC 問題B は、まさに「スコア計算だけ」やらせる入門問題だ。

**霊夢**: ビジュアライザは？

**魔理沙**: 解を**目で見る**ツール。経路問題なら線が描かれる、配置問題なら盤面が見える。バグ（合法でない操作）や改善のヒントが一発でわかることが多い。**使わない手はない**んだ。

**霊夢**: 提出の流れは？

**魔理沙**: 典型フローはこうだ。

```
1. 問題文・スコア式・入力形式を読む
2. スコア計算関数を実装する
3. とにかく合法解を1つ出す（ランダム / 貪欲 / 手作り）
4. ビジュアライザ / スコアで確認
5. 近傍操作 + 山登り / 焼きなまし等で改善
6. TL 手前で最良解を出力
7. AtCoder に提出 → 5分待って再提出
```

```python
# python/ch01/submit_flow.py — 提出前チェックリスト（擬似コード）
def pre_submit_checks(output, validator, score_fn, timer):
    assert validator(output), "illegal output"
    score = score_fn(output)
    assert timer.elapsed() < timer.limit, "TLE locally"
    print("score:", score, file=__import__("sys").stderr)
    return output
```

```go
// go/ch01/submit_flow.go — 最良解を保持するパターン
package main

import "fmt"

type State struct {
	Score int
	Data  []int
}

func bestSoFar(current, best State) State {
	if current.Score > best.Score {
		return current
	}
	return best
}

func main() {
	best := State{Score: -1}
	// 探索ループの中で best = bestSoFar(candidate, best)
	best = bestSoFar(State{Score: 100, Data: []int{1, 2}}, best)
	best = bestSoFar(State{Score: 250, Data: []int{3, 4}}, best)
	fmt.Println(best)
}
```

**霊夢**: Intro HC のスコア式、具体的にはどうなってるの？

**魔理沙**: 問題A（コンテスト日程）では、365日間の満足度 `S` に対して

$$\text{score} = \max(10^6 + S,\ 0)$$

テストケース50個の**合計**が提出スコアだ。問題B では各日の満足度 `v_d` を出力する——スコア計算の練習用だな。

**霊夢**: 満足度の更新ルールは？

**魔理沙**: 各日 `d` について:

1. その日のコンテストタイプ `t_d` を開催 → 満足度 `+ s_{d,t_d}`
2. 日末に、各タイプ `i` について `c_i × (d - last(d,i))` だけ満足度が**減る**
   - `last(d,i)` = 日 `d` 以前（`d` 含む）でタイプ `i` を最後に開催した日
   - 一度も開催していなければ `last = 0`

```python
# python/ch01/score_intro_hc.py — コア部分（抜粋）
def daily_satisfactions(d, c, s, schedule):
    last = [0] * 26
    satisfaction = 0
    result = []
    for day in range(1, d + 1):
        t = schedule[day - 1] - 1
        satisfaction += s[day - 1][t]
        last[t] = day
        decay = sum(c[i] * (day - last[i]) for i in range(26))
        satisfaction -= decay
        result.append(satisfaction)
    return result
```

```go
// go/ch01/score_intro_hc.go — 同じロジック（抜粋）
for day := 1; day <= d; day++ {
    t := schedule[day-1] - 1
    satisfaction += s[day-1][t]
    last[t] = day
    decay := 0
    for i := 0; i < 26; i++ {
        decay += c[i] * (day - last[i])
    }
    satisfaction -= decay
    result = append(result, satisfaction)
}
```

**霊夢**: `max(10^6 + S, 0)` の `10^6` は何？

**魔理沙**: 満足度がマイナスでも**提出自体は意味がある**ようにするオフセットだ。S が -500000 なら 500000 点、S が -2000000 なら 0 点になる。

### Step 3: 改変 — 日程を変えてスコアを比較

```python
# python/ch01/compare_schedules.py
import subprocess
import sys
from pathlib import Path

ROOT = Path(__file__).resolve().parents[2]
SAMPLE = ROOT / "data" / "ch01" / "sample.txt"
SCORER = ROOT / "python" / "ch01" / "score_intro_hc.py"


def run_with_schedule(schedule: list[int]) -> tuple[list[int], int]:
    lines = SAMPLE.read_text().splitlines()
    # 末尾 D 行が日程
    d = int(lines[0])
    body = lines[: 1 + 1 + d]  # D, c, s rows
    text = "\n".join(body + [str(x) for x in schedule]) + "\n"
    proc = subprocess.run(
        [sys.executable, str(SCORER)],
        input=text,
        text=True,
        capture_output=True,
        check=True,
    )
    daily = list(map(int, proc.stdout.split()))
    final = int(proc.stderr.strip())
    return daily, final


if __name__ == "__main__":
    # サンプル日程 vs 全部タイプ1
    d = 5
    orig = [1, 17, 13, 14, 13]
    all_one = [1] * d
    for name, sched in [("sample", orig), ("all_type1", all_one)]:
        daily, final = run_with_schedule(sched)
        print(name, "final_score=", final, "last_day=", daily[-1])
```

### Step 4: コンテスト形式 — 問題A へつなぐ

問題B の次のステップ（公式ガイド）は、**各日いちばん満足度が高くなるタイプを貪欲に選ぶ**こと。問題A 本体は [Intro HC 問題A](https://atcoder.jp/contests/intro-heuristics/tasks/intro_heuristics_a) だ。

```python
# python/ch01/greedy_intro_hc.py — 問題A 向け貪欲の骨格（D=365 想定）
def greedy_schedule(d, c, s, daily_satisfactions_fn):
    last = [0] * 26
    satisfaction = 0
    schedule = []
    for day in range(1, d + 1):
        best_t, best_sat = 1, None
        for t in range(1, 27):
            trial = schedule + [t]
            sat = daily_satisfactions_fn(day, c, s, trial)[-1]
            if best_sat is None or sat > best_sat:
                best_sat = sat
                best_t = t
        schedule.append(best_t)
    return schedule
```

```go
// go/ch01/greedy_intro_hc.go — 骨格のみ（詳細は第5章）
// 各日 26 通り試して、その日終了時満足度が最大のタイプを選ぶ
func greedySchedule(d int, c []int, s [][]int, scoreFn func([]int) []int) []int {
    schedule := make([]int, 0, d)
    for day := 1; day <= d; day++ {
        bestT, bestSat := 1, int(-1e18)
        for t := 1; t <= 26; t++ {
            trial := append(append([]int{}, schedule...), t)
            sat := scoreFn(trial)[len(trial)-1]
            if sat > bestSat {
                bestSat = sat
                bestT = t
            }
        }
        schedule = append(schedule, bestT)
    }
    return schedule
}
```
