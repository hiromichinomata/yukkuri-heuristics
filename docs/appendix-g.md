**霊夢**: 章ごとにいろいろ学んだけど、1 問を最初から最後まで通して解いたことがないの。

**魔理沙**: この付録でやる。[Introduction to Heuristics Contest 問題A](https://atcoder.jp/contests/intro-heuristics/tasks/intro_heuristics_a)（以下 Intro HC）を、本書のコードだけで段階的に強くしていく。各段で **手元で採点 → 提出できる形か確かめる** をくり返すんだ。

## G.1 問題とゴール

| 項目 | 内容 |
|------|------|
| 入力 | D = 365 日、26 種類のコンテストの減衰 c_i（0〜100）と、各日・各タイプの満足度 s_{d,i}（0〜20000） |
| 出力 | 各日に開くタイプ（1〜26）を 365 行 |
| 得点 | 1 ケースあたり max(10^6 + 満足度, 0)。本番は 50 ケースの合計 |
| 制限時間 | 2 秒 |

満足度とスコアの計算は第1章、State / Move / Score の整理は第3章でやった。

**霊夢**: ゴールは？

**魔理沙**: 「0 点の解」から始めて、手元の平均で **200 万点** を超えるところまでだ。

## G.2 手元の採点環境

**魔理沙**: 1 つの入力だけで良し悪しを決めると、たまたまの当たり外れにだまされる。seed を変えた入力をいくつも作り、平均で比べる。`tools/eval_intro_hc.py` がそれをまとめてやってくれる。

```bash
python tools/eval_intro_hc.py -- python python/ch02/sample_solver.py
```

```text
seed=1 score=0 time=0.03s ok
seed=2 score=0 time=0.04s ok
seed=3 score=0 time=0.03s ok
seed=4 score=0 time=0.03s ok
seed=5 score=0 time=0.03s ok
average=0 max_time=0.04s
```

（時間はマシン速度で変わる。）

- seed 1〜5 の入力（D=365）を作り、`--` のあとのコマンドに stdin で渡す。seed 1 の入力は `data/common/intro_hc_d365.txt` と同じだ。
- 出力を第1章の `score_intro_hc.py` と同じ式で採点する。行数が違う・1〜26 以外の値があれば 0 点（本番の WA の代わり）。
- 実行時間が 2 秒を超えたら `TLE` と出る。`--seeds 10` で入力を増やせる。

## G.3 段階ごとに強くする

手元で測った結果をまとめると、次のようになる（seed 1〜5 の平均。時間で打ち切る段は、動かすたびに数万ずつぶれる）。

| 段 | 使うコード | 平均スコア | 最大時間 | 判定 |
|----|-----------|-----------|---------|------|
| 0 | 毎日タイプ 1（第2章 `sample_solver.py`） | 0 | 0.04 秒 | 提出はできるが 0 点 |
| 1 | 貪欲（第1章 `greedy_intro_hc.py`） | 1093253 | 6.84 秒 | **TLE** |
| 2 | 焼きなまし・差分更新（第9章 `sa_intro_hc.py`） | 1293021 | 1.57 秒 | ok |
| 3 | 貪欲 → 山登り → 焼きなまし（第11章 `pipeline.py`） | 1986934 | 1.90 秒 | ok |
| 4 | 第9章の Go 版 | 2029563 | 1.55 秒 | ok |
| 5 | 近傍を 2 種類に（第16章の Go 版） | 2110526 | 1.54 秒 | ok |

### 段 0: まず提出できる形にする

**霊夢**: 毎日タイプ 1 だと 0 点なの？ 第2章のサンプル（D=5）では 104 万点だったのに。

**魔理沙**: D=5 なら減衰がたまる前に終わるが、365 日も同じタイプだけだと、残り 25 種類の減衰が毎日積み上がって、満足度が大きくマイナスになる。0 で切られて 0 点だ。それでも **形式が正しい解を最初に提出する** のは大事だ（第2章 2.6 のチェックリスト）。No Submit よりはずっといい。

### 段 1: 貪欲 — 強いが遅い

```bash
python tools/eval_intro_hc.py -- python python/ch01/greedy_intro_hc.py
```

```text
seed=1 score=551804 time=6.84s TLE
...
average=1093253 max_time=6.84s
```

（時間はマシン速度で変わる。）

**魔理沙**: スコアは一気に 100 万を超えるが、1 ケース 5〜7 秒で **TLE** だ。第1章の貪欲は、1 日決めるたびにスケジュール全体を計算し直している（O(26²·D²)）。

**霊夢**: 第1章の演習4で、O(26²·D) に直したやつね。

**魔理沙**: そうだ。その解答例に差し替えると、同じスコアのまま、貪欲の計算時間は数秒から 0.002 秒ほどになる。**スコアだけでなく時間も必ず見る**——手元の採点で TLE を出しておけば、本番で気づくより何倍もましだ。

### 段 2: 焼きなまし（Python）

```bash
python tools/eval_intro_hc.py -- python python/ch09/sa_intro_hc.py
```

**魔理沙**: 第9章の SA は 1.5 秒で打ち切るので、時間は安全だ。ただ、ランダムな初期解から始めるので、Python の手数（1.5 秒で約 2.5 万手）では平均 129 万点止まり。差分更新（第9章 9.4）がなければ、この 1/100 も回らない。

### 段 3: 貪欲から始める多段パイプライン

```bash
python tools/eval_intro_hc.py -- python python/ch11/pipeline.py
```

**魔理沙**: 第11章のパイプラインは、速い貪欲で 55 万点前後の初期解を作り、山登り、SA と続ける。同じ Python でも平均 199 万点まで上がる。**初期解を賢くすると、残りの時間を「良い解の近く」を探すのに使える**。

**霊夢**: 時間は 1.90 秒って、ぎりぎりなの。

**魔理沙**: パイプラインは 1.8 秒で打ち切るが、Python の起動と入出力に 0.1 秒ほどかかる。本番のジャッジは手元より遅いこともあるので、2 秒の問題で 1.8 秒以上使うのは攻めすぎだ。不安なら `TOTAL_SEC` を 1.6 に下げる。

### 段 4・5: Go に移す、近傍を増やす

```bash
go build -o /tmp/sa_go go/ch09/sa_intro_hc.go
python tools/eval_intro_hc.py -- /tmp/sa_go
go build -o /tmp/sa_multi go/ch16/sa_multi_neighborhood.go
python tools/eval_intro_hc.py -- /tmp/sa_multi
```

**魔理沙**: Go に移すと、同じ SA でも 1.5 秒で約 70 万手——Python の約 30 倍——回せて、ランダムな初期解からでも平均 203 万点に届く。さらに第16章の「1 日変更 + 2 日入れ替え」の 2 種類の近傍にすると 211 万点。

**霊夢**: `go run` じゃなくて `go build` するのはなぜ？

**魔理沙**: `go run` は毎回ビルドするので、その時間まで実行時間に入ってしまう。ビルドしたものを渡せば、AtCoder と同じく実行だけの時間が測れる。それでも、ビルドしたての 1 回目だけ起動に時間がかかって、手元では 2 秒を超えたことがあった。TLE が出たら、もう一度測って確かめる。

## G.4 振り返り — 何が一番効いたか

| 変更 | 平均スコアの伸び | 本書の章 |
|------|----------------|---------|
| 合法な解を出す | 0 → 0（でも提出できた） | 第2章 |
| 貪欲（時間を直せば） | 0 → 約 109 万 | 第1章 |
| ランダム初期解の SA | 約 129 万 | 第9章 |
| 貪欲の初期解 + 山登り + SA | 約 199 万 | 第11章 |
| Python → Go（手数 30 倍） | 約 203 万（ランダム初期解のまま） | 第28章 |
| 近傍を 2 種類に | 約 211 万 | 第16章 |

**霊夢**: Python のパイプラインと、Go の素の SA がほぼ同じなの。

**魔理沙**: そこが面白いところだ。**言語を速くするのと、アルゴリズムを賢くするのは、同じくらい効く**。どちらが先かは問題しだいだが、Python で設計を固め、最後に Go に移すのが本書のおすすめの順番だ（第28章 28.3）。Go 版のパイプラインに近傍を足せば、さらに上を狙える。

## G.5 提出する

1. AtCoder で言語を選ぶ（Python なら「Python (CPython)」か「Python (PyPy)」、Go なら「Go」）。
2. ファイルの中身をそのまま貼る。stdout には日程だけを出し、ログは stderr に出す（本書のコードはそうなっている）。
3. 提出結果の得点が、手元の平均 × 50 くらいになっているか見る。大きくずれたら、入力の読み方か、時間の使い方を疑う。

**魔理沙**: PyPy にすると Python でも手数が数倍になることが多い。第11章のパイプラインを PyPy で出してみるのも試す価値がある（第28章 28.1）。
