## 26.1 自作ビジュアライザの設計

**霊夢**: 橙色になると、公式 vis が無い問題も多いの？

**魔理沙**: そうだ。**ビジュアライザ駆動開発** は「スコアだけ見る」のではなく、**解がどう見えるか** を先に固めるやり方だ。設計の要点は次の4つ。

| 要素 | 役割 |
|------|------|
| **入力フォーマット** | グリッド・経路・配置を1ファイルにまとめる |
| **レンダラ** | ASCII / HTML / PNG など、環境に合わせて選ぶ |
| **オーバーレイ** | 壁・開始・ゴールの上に経路や操作を重ねる |
| **メタ情報** | stderr に `path_len` や legend を出す |

**霊夢**: 最初から GUI を作るの？

**魔理沙**: 不要だ。**ASCII グリッド** ならターミナルだけで回る。第26章の `simple_vis` は `data/ch26/sample.txt` を読み、壁 `#`・開始 `S`・ゴール `G`・経路 `*` を描く。

入力フォーマット（共通）:

```text
N
grid row 0 ... row N-1    # 0=空 1=壁 2=開始 3=ゴール
path_len
r0 c0
r1 c1
...
```

Python の読み込み:

```python
# python/ch26/simple_vis.py
@dataclass
class VisInput:
    n: int
    grid: List[List[int]]
    path: List[Tuple[int, int]]

def read_vis(stream: TextIO) -> VisInput:
    lines = [ln.strip() for ln in stream.read().splitlines() if ln.strip()]
    n = int(lines[0])
    grid = [list(map(int, lines[i + 1].split())) for i in range(n)]
    path_len = int(lines[n + 1])
    path = [tuple(map(int, lines[n + 2 + i].split())) for i in range(path_len)]
    return VisInput(n=n, grid=grid, path=path)
```

Go も同じ行順:

```go
// go/ch26/simple_vis.go
type VisInput struct {
    N    int
    Grid [][]int
    Path [][2]int
}
```

**霊夢**: Python と Go で見た目を揃えるの？

**魔理沙**: **フォーマットを先に決める** のがコツだ。レンダラは言語ごとに違っても、**同じ `sample.txt`** を食わせれば diff が取れる。

## 26.2 デバッグと解法改善への活用

**霊夢**: スコアが伸びないとき、vis で何を見るの？

**魔理沙**: 典型パターンは3つ。

1. **制約違反の形** — 重なり・未訪問・壁貫通が一目で分かる
2. **無駄な迂回** — 経路がループやデッドエンドに入っている
3. **局所最適の「形」** — 同じスコア帯で形が似ている → 近傍が足りない

オーバーレイの核心:

```python
def overlay_path(grid, path):
    view = [[CELL_CHARS.get(grid[r][c], "?") for c in range(n)] for r in range(n)]
    for r, c in path:
        if grid[r][c] in (2, 3):   # S/G は上書きしない
            continue
        view[r][c] = PATH_CHAR  # "*"
    return view
```

**霊夢**: デバッグは print より vis が速い？

**魔理沙**: **空間問題** では圧倒的に速い。数値ログだけだと「どのセルが悪いか」が分からない。vis を見て **近傍操作を1つ足す** — それが26.5演習の流れだ。

改善ループ:

```
解法を走らせる → vis 出力 → 形を観察 → 近傍/初期解を修正 → 再実行
```

stderr 例:

```
legend: . empty  # wall  S start  G goal  * path
grid=8 path_len=7
```

**path_len** が想定より短い・長いとき、経路生成側のバグを vis 側で切り分けられる。

## 26.3 スコア分布・操作履歴の可視化

**霊夢**: 解の形だけじゃなく、スコアの推移も見たいの。

**魔理沙**: 橙色帯では **探索ログ** も vis の対象にする。

| 可視化対象 | 形式 | 用途 |
|-----------|------|------|
| スコア時系列 | CSV → 折れ線 | SA の冷却・受理率の確認 |
| 操作履歴 | `(turn, op, delta)` リスト | どの操作が効いたか |
| スコア分布 | ヒストグラム | multi-start の谷の数 |

簡易スコアログ（解法側 stderr）:

```python
# 探索ループ内
if step % 1000 == 0:
    print(f"log score={best} step={step}", file=sys.stderr)
```

操作履歴を vis 入力に載せる拡張例:

```text
# sample_with_ops.txt（拡張案）
N
... grid ...
path_len
... path ...
ops_len
swap 3 4 +120
relocate 1 7 -40
```

HTML 出力は `--html` で共有しやすい:

```bash
python python/ch26/simple_vis.py --html data/ch26/sample.txt > vis.html
go run go/ch26/simple_vis.go -html -input data/ch26/sample.txt > vis.html
```

**霊夢**: 本番コンテスト中も vis を回す？

**魔理沙**: **ローカル専用** が基本。提出バイナリに matplotlib は載せない。ASCII か軽量 HTML を **オフライン生成** する。

## 26.4 ハンズオン: Python / Go 共通フォーマットの簡易ビジュアライザ

**霊夢**: 実際に動かすの？

**魔理沙**: `data/ch26/sample.txt` で確認するぜ。

### Step 1: 読む

`sample.txt` は 8×8 グリッド、経路7ステップ。壁 `#` に囲まれた S→G への道が `*` で見える。

### Step 2: 写す（実行）

```bash
python python/ch26/simple_vis.py < data/ch26/sample.txt
go run go/ch26/simple_vis.go -input data/ch26/sample.txt
```

期待出力（ASCII 抜粋）:

```text
+---------------+
| . . # . . . . . |
| . S . # . . . . |
| . * * . # . . . |
| . . * . . . . . |
| # # * * . . . G |
+---------------+
```

HTML:

```bash
python python/ch26/simple_vis.py --html data/ch26/sample.txt > /tmp/ch26.html
open /tmp/ch26.html   # macOS
```

### Step 3: 改変（経路を差し替え）

`sample.txt` の path 部分だけ書き換え、**同じ grid で別経路** を比較する。

```text
7
1 1
2 1
3 1
4 1
4 2
4 3
5 3
```

→ 壁 `#` にぶつかる経路なら `*` が壁セルに乗る。制約チェック vis として使える。

### Step 4: コンテスト形式（解法と接続）

解法が経路を stdout に出すなら、vis 用ファイルに整形して渡す:

```bash
# 自分の解法の出力を ch26 フォーマットに合わせて path.txt を作る
python python/ch26/simple_vis.py path.txt
```

**パイプライン**: `[solver] → [path file] → [simple_vis] → 目視 → [近傍追加]`
