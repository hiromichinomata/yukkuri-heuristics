# 第12章 インタラクティブ問題

> **到達目標（水色帯 1200〜1599）**: インタラクティブ入出力を正しく回し、クエリごとに推定を更新するオンライン解法を設計できる。

---

## 12.1 インタラクティブ問題の入出力形式

**霊夢**: インタラクティブって、ジャッジと会話しながら解くタイプなの？

**魔理沙**: そうだ。普通の問題は「入力を全部読んでから答えを出す」が、インタラクティブ問題は **ジャッジと1往復ずつ** やり取りする。代表例が [AHC003「Shortest Path Queries」](https://atcoder.jp/contests/ahc003/tasks/ahc003_a) だ。30×30 のグリッドで、辺の長さは隠されている。

| 順番 | 向き | 内容（AHC003） |
|------|------|----------------|
| 1 | ジャッジ → あなた | `si sj ti tj`（始点と終点） |
| 2 | あなた → ジャッジ | 経路を `U` `D` `L` `R` の文字列で1行 |
| 3 | ジャッジ → あなた | その経路の長さ b にノイズ（0.9〜1.1 倍）を掛けた整数 |
| 繰り返し | | 1000 クエリ |

**魔理沙**: 返ってくるのは **ノイズ付きの長さ1つだけ** だ。どの辺が長かったかは教えてくれない。スコアは「真の最短距離 / 自分の経路の長さ」を、後半のクエリほど重く足し合わせたもの——つまり **推定を早く正確にして、後半で最短経路を出す** のが勝負になる。

**霊夢**: 普通の「入力を全部読んでから出力」と何が違うの？

**魔理沙**: **答えを出したら、すぐ flush して返事を待つ** 点だ。出力をバッファに溜めたまま次の入力を読もうとすると、ジャッジは経路を待ち、こちらは返事を待ち——**お互い待ったまま止まる**（TLE になる）。

```python
# python/ch12/solver.py — 対話ループ
def main() -> None:
    solver = Solver()
    while True:
        line = sys.stdin.readline()
        if not line.strip():
            break  # 入力の終わり
        si, sj, ti, tj = map(int, line.split())
        path, edges, predicted = solver.shortest_path(si, sj, ti, tj)
        print(path, flush=True)  # flush しないとジャッジが返事を待ったまま止まる
        observed = int(sys.stdin.readline())
        solver.update(edges, predicted, observed)
```

```go
// go/ch12/solver.go — 同じ対話ループ
path, edges, predicted := solver.shortestPath(q[0], q[1], q[2], q[3])
fmt.Fprintln(out, path)
out.Flush() // bufio.Writer は Flush するまで実際には書き出さない
line, _ = in.ReadString('\n')
observed, _ := strconv.Atoi(strings.TrimSpace(line))
solver.update(edges, predicted, observed)
```

**霊夢**: 本番のジャッジがないと試せないの？

**魔理沙**: そのために `python/ch12/local_judge.py` を用意した。ソルバを子プロセスとして起動し、本番と同じ手順で会話して、公式と同じ式でスコアを出す。辺の長さの生成だけは簡略版だ。

## 12.2 オンラインアルゴリズムの考え方

**霊夢**: オンラインって、未来のクエリが見えないってこと？

**魔理沙**: その通り。**今のクエリに答える時点では、後のクエリも真の辺の重みも分からない**。だから「今わかっている情報だけ」で最善を尽くし、**フィードバックで信念を更新**する。

```
  時刻 →
  ┌─────────┐    ┌─────────┐    ┌─────────┐
  │ Query 1 │ →  │ Query 2 │ →  │ Query 3 │
  │ 推定で答│    │ 更新後  │    │ さらに  │
  └─────────┘    └─────────┘    └─────────┘
       ↑              ↑
   観測した長さ    観測した長さ
```

**霊夢**: 最初は辺の長さが分からないのに、どうやって経路を選ぶの？

**魔理沙**: 本リポジトリの `Solver` は、全部の辺を **推定値 5000** で始める（本番の辺の長さはだいたい 1000〜9000）。横の辺を `h`、縦の辺を `v` の2次元配列で持つ。

```python
# python/ch12/solver.py
class Solver:
    def __init__(self) -> None:
        self.h = [[INIT_WEIGHT] * (N - 1) for _ in range(N)]  # (i,j)-(i,j+1)
        self.v = [[INIT_WEIGHT] * N for _ in range(N - 1)]  # (i,j)-(i+1,j)
```

**霊夢**: 推定がズレてると、ダイクストラの答えも本当の最短経路からズレるわけね。

**魔理沙**: そう。だから **推定を真に近づける更新** が本体になる。スコアは「真の最短距離 / 自分の経路の長さ」なので、推定が良くなるほど後半のクエリで点が取れる。

## 12.3 探索と利用のバランス（多腕バンディットの入門）

**霊夢**: 多腕バンディットって、スロット機の比喩？

**魔理沙**: **複数の選択肢（腕）** から毎ターン1つ選び、報酬をもらう模型だ。AHC003 では「どの辺を信じるか」「どの経路を試すか」に対応づけられる。

| 方針 | 意味 | インタラクティブでの例 |
|------|------|------------------------|
| **利用（Exploit）** | 今いちばん良さそうな手 | 推定重みで最短経路を出す |
| **探索（Explore）** | 情報が少ない所を試す | あまり使わない辺を通る経路を意図的に選ぶ |

**霊夢**: 第12章のコードは探索してない？

**魔理沙**: 第12章のソルバは **利用寄り**（推定でダイクストラ）＋ **返ってきた長さで、通った辺をまとめて伸び縮み** だ。探索を足すなら「不確かな辺を通る経路」をわざと選ぶ **Thompson sampling / UCB** が次のステップ（第24章）だぜ。

```python
# python/ch12/solver.py
def update(self, edges, predicted, observed):
    # 観測 / 予測 > 1 なら「思ったより長かった」→ 通った辺を伸ばす
    factor = 1.0 + LEARNING_RATE * (observed / predicted - 1.0)
    for kind, i, j in edges:
        table = self.h if kind == 0 else self.v
        table[i][j] = min(W_MAX, max(W_MIN, table[i][j] * factor))
```

```go
// go/ch12/solver.go
func (s *Solver) update(edges []Edge, predicted float64, observed int) {
	factor := 1.0 + learningRate*(float64(observed)/predicted-1.0)
	for _, e := range edges {
		w := s.weight(e)
		*w = math.Min(wMax, math.Max(wMin, *w*factor))
	}
}
```

**霊夢**: `LEARNING_RATE` は何のため？

**魔理沙**: 観測には **±10% のノイズ** が乗っているから、1回のずれをそのまま信じると振り回される。半分だけ反映して、何度も通るうちに平均が合ってくるようにしている。上位解法は「行ごとに長さが似ている」という生成の性質まで使って、もっと賢く推定する。

## 12.4 クエリ回数・情報更新の設計

**霊夢**: クエリは何回でも打てるわけじゃないのよね？

**魔理沙**: **クエリ上限 Q** と **1クエリのコスト**（時間・スコア）をセットで設計する。

| 設計ポイント | 内容 |
|-------------|------|
| 更新の粒度 | 経路全体を一括か、辺1本ずつか |
| 数値の安定 | `W_MIN` / `W_MAX` でクリップ、学習率で振れ幅を抑える |
| 再計算コスト | ダイクストラは `O((V+E) log V)`。900 頂点 × 1000 クエリなら Python でも間に合う |
| ノイズ | 1回の観測を信じすぎない（学習率・平均化） |

**霊夢**: ダイクストラは Python が heapq、Go は？

**魔理沙**: Go も `container/heap` で優先度キューにしている。取り出す順（距離が同じなら行・列の小さい順）まで Python と揃えてあるので、**同じジャッジの seed なら Python 版と Go 版は同じ経路・同じスコア** になる。

```python
# 骨格: ダイクストラの入口（実物の python/ch12/solver.py は格子上なので (d, i, j) を積む）
def dijkstra(adj, start, goal):
    pq = [(0.0, start)]
    while pq:
        d, u = heapq.heappop(pq)
        if d > dist[u]:
            continue
        # ...
```

**霊夢**: `edge(i, j, ni, nj)` で `min` を取ってるのはなぜ？

**魔理沙**: 辺は向きがないから、(i,j)→(i,j+1) と (i,j+1)→(i,j) を **同じ配列の要素** に対応させるためだ。そうしないと、同じ辺を別物として推定してしまう。

## 12.5 ハンズオン: AHC003「Shortest Path Queries」— 重み更新 + ダイクストラ

**霊夢**: 手を動かす章だ。何から実行すればいい？

**魔理沙**: 4ステップだ。**読む → 写す → 改変 → コンテスト形式**。

### Step 1: ローカルジャッジで動かす

```bash
cd /path/to/yukkuri-heuristics
python python/ch12/local_judge.py --seed 1 -- python python/ch12/solver.py
```

`--` のあとがソルバの起動コマンドだ。ジャッジがソルバを子プロセスとして起動し、1000 クエリ会話する。stderr の最後に結果が出る:

```text
seed=1 queries=1000 score=920496769 max=999999910 ratio=0.9205 elapsed=1.49s
```

（`elapsed` だけはマシン速度で変わる。`score` は seed が同じなら同じになる。）

**霊夢**: `max` は何？

**魔理沙**: 全クエリで真の最短経路を出せたときの点だ。`ratio=0.92` は「最短経路の 92% くらいの質」という目安になる。推定の初期値 5000 のままダイクストラすると、もっと低い。

### Step 2: Go のソルバも同じジャッジで

```bash
python python/ch12/local_judge.py --seed 1 -- go run go/ch12/solver.go
```

**同じスコア 920496769** になる。ジャッジは Python のまま、ソルバだけ差し替えられるのがローカルジャッジの便利なところだ。

### Step 3: 改変 — 学習率と初期値

`solver.py` の `LEARNING_RATE` を `0.2 / 0.5 / 0.8`、`INIT_WEIGHT` を `3000 / 5000 / 7000` に振り、`--seed 1〜5` の平均スコアを表にする。

```bash
for s in 1 2 3 4 5; do python python/ch12/local_judge.py --seed $s -- python python/ch12/solver.py; done
```

### Step 4: コンテスト形式で気をつけること

| 確認 | 理由 |
|------|------|
| 出力のたびに flush | 忘れると待ち合わせで止まり TLE |
| 同じ頂点を2回通らない | 本番では WA（ジャッジも同じチェックをする） |
| 入力の終わりで正しく終了 | 1000 クエリ後に読み続けて止まらない |

### ジャッジとの対応

| `local_judge.py` | AHC003 本番 |
|------------------|-------------|
| 入出力の手順・WA 判定・スコア式 | **同じ** |
| クエリ数 `--queries`（既定 1000） | 1000 |
| 辺の長さの生成 | 簡略版（本番は行・列を2分割するなど、もう少し複雑） |

## 12.6 演習

1. `--queries 100` と `--queries 1000` で `ratio` を比べ、クエリが増えると推定が良くなることを確かめる。
2. `LEARNING_RATE = 1.0`（観測をそのまま信じる）にしてスコアを測り、ノイズに振り回される様子を見る。
3. `solver.py` の `print(path, flush=True)` から `flush=True` を外して実行し、何が起きるか確かめる（止まったら Ctrl+C）。
4. 探索寄りに、最初の 100 クエリだけ「推定の短い経路」ではなく「まだ通っていない辺を多く通る経路」を選ぶ戦略を考え、スコアの変化を予想する（実装は任意。第24章へ続く）。
5. AHC003 の公式問題文を開き、**スコアの式でなぜ後半のクエリが重いのか** を第3章のテンプレで整理する。
