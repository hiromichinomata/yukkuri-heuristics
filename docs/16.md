## 16.1 適応的冷却（Adaptive Cooling）

**霊夢**: 第9章は経過時間だけで温度が決まる、固定のスケジュールだったよね？

**魔理沙**: そうだ。時間ベースは「最後まで温度が残る」のが長所だが、探索の様子は見ていない。**適応的冷却** は「改善が続いているか」で **α（冷却率）を変える**。伸びているうちは速く冷やし（`ALPHA_FAST`）、停滞したらゆっくり（`ALPHA_SLOW`）——局所で粘る。

```python
# python/ch16/sa_multi_neighborhood.py
ALPHA_FAST = 0.992
ALPHA_SLOW = 0.998
since_improve = 0

if since_improve > 200:
    alpha = ALPHA_SLOW
temperature *= alpha
```

```go
// go/ch16/sa_multi_neighborhood.go — 同様の sinceImprove / alpha 切替
```

| フェーズ | α | 意図 |
|---------|---|------|
| 探索初期 | 大きい冷却（速く冷える） | 広く歩く |
| 停滞気味 | 小さい冷却 | 細かい改善を拾う |

**霊夢**: 温度ログは stderr？

**魔理沙**: `sa step=... T=...` を出す。本番では **best と current と T** をセットで見ると調整が速い。

## 16.2 複数近傍の切り替え（Neighborhood Portfolio）

**霊夢**: 近傍って1種類じゃだめ？

**魔理沙**: 問題によって **効く操作が違う**。複数登録し、**改善に寄与した近傍に重み** を寄せる——ポートフォリオだ。

```python
neighborhoods = [
    ("change_day", neighbor_change_day),   # 1 日の種類を変更
    ("swap_days", neighbor_swap_days),     # 2 日をスワップ
]
weights = [1.0, 1.0]
wins = [0, 0]

idx = rng.choices(range(len(neighborhoods)), weights=weights, k=1)[0]
name, neigh_fn = neighborhoods[idx]
nxt = neigh_fn(state, rng)
```

500 ステップごとに `wins` から重みを更新:

```python
total = sum(wins) or 1
weights = [max(0.2, w / total * 2) for w in wins]
```

**霊夢**: 実際の AHC だとどんな近傍を混ぜるの？

**魔理沙**: 配置問題なら「1個動かす」「2個入れ替える」「回転する」、経路問題なら「2-opt」「1点挿し替え」など、**性質の違う局所操作** を混ぜるのが典型だ。第16章は Intro HC 互換の **日程スケジュール** で同じ骨格を示す。

## 16.3 再ヒート（Reheating）

**霊夢**: 冷え切ったら終わり？

**魔理沙**: **再ヒート** で温度を戻し、もう一度悪化受理を強くする。`STAGNANT_LIMIT` ステップ best が更新されなければ発火。

```python
REHEAT_FACTOR = 0.6
STAGNANT_LIMIT = 800

if since_improve >= STAGNANT_LIMIT:
    temperature = max(temperature, T0 * REHEAT_FACTOR)
    since_improve = 0
    alpha = ALPHA_FAST
    print(f"reheat T={temperature:.1f}", file=sys.stderr)
```

```
スコア
  ^     /\      reheat後また揺れる
  |    /  \___/\
  |   /        \___
  +------------------→ 時間
```

**霊夢**: 無限に reheat したら？

**魔理沙**: **時間制限** で打ち切る。`TIME_LIMIT_SEC = 1.5` のように `time.perf_counter()` でループを切るのが本番作法（第9章・第11章と同じ）。

### 受理判定のおさらい（第9章との接続）

```python
delta = new_score - score
accepted = delta >= 0 or rng.random() < math.exp(delta / temperature)
```

再ヒート後は **T が大きい** ため、しばらく悪化も通りやすい。`since_improve` は **best が更新されたときだけ 0** にリセットするのが第16章の実装だ。

| ログ | 読み方 |
|------|--------|
| `score=` | 現在解（悪化していることもある） |
| `best=` | 提出候補（歴代最高） |
| `nh=` | 直近で選ばれた近傍名 |
| `wins=` | 近傍ごとの改善寄与カウント |

## 16.4 終盤の決め技（Large Neighborhood Search の入門）

**霊夢**: LNS って第19章じゃないの？

**魔理沙**: **入門** としてここで触れる。**広い近傍**＝解の一部を大きく壊して、残りを貪欲や短い SA で直す。第16章の `swap_days` は2日だけだが、終盤に **連続10日をランダム再生成** する近傍を1つ足すと LNS の味がする。

| 近傍の規模 | 例 | コスト |
|-----------|-----|--------|
| 小 | 1 日変更 | 低 |
| 中 | 2 日スワップ | 低 |
| 大（LNS 風） | 連続区間を再構築 | 高・強力 |

**霊夢**: 終盤だけ大近傍？

**魔理沙**: よくある。**残り時間 < 20%** のときだけ LNS 的近傍を混ぜる。青色の第19章で Destroy & Repair を本格化する。

### Step 2: 近傍の追加

```python
def neighbor_shuffle_block(state, rng):
    nxt = ScheduleState(list(state.types))
    a, b = sorted(rng.sample(range(len(nxt.types)), 2))
    block = nxt.types[a:b]
    rng.shuffle(block)
    nxt.types[a:b] = block
    return nxt
```

`neighborhoods` に登録し、`wins` の長さを3に合わせる。stderr の `wins=` で **どの近傍が伸ばしたか** を見る（16.6 演習）。

### Step 3: 冷却・再ヒートのチューニング

STAGNANT_LIMIT = 400   # reheat を早める

### Step 4: 配置問題への対応

| 第16章 | 配置問題に置き換えると |
