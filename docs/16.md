## 16.1 適応的冷却（Adaptive Cooling）

**霊夢**: 第9章は経過時間だけで温度が決まる、固定のスケジュールだったよね？

**魔理沙**: そうだ。時間ベースは「最後まで温度が残る」のが長所だが、探索の様子は見ていない。**適応的冷却** は「改善が続いているか」を見て温度の動きを変える。第16章では、時間ベースの基準温度に **倍率 `boost`** を掛ける形にする。

```text
T = T0 * (T1 / T0) ** progress * boost     # boost は 1 以上。1 に向かって減っていく
```

**魔理沙**: boost が 1 に戻る速さを状況で変える。伸びているうちは速く戻し（`BOOST_DECAY_FAST`）、停滞気味ならゆっくり戻す（`BOOST_DECAY_SLOW`）——熱いまま粘って局所から抜ける。

```python
# python/ch16/sa_multi_neighborhood.py
T0, T1 = 5000.0, 10.0
BOOST_DECAY_FAST = 0.999
BOOST_DECAY_SLOW = 0.9999
SLOW_AFTER = 2000  # best 更新がこのステップ数ないと「停滞気味」

temperature = T0 * (T1 / T0) ** progress * boost
# ...
decay = BOOST_DECAY_SLOW if since_improve > SLOW_AFTER else BOOST_DECAY_FAST
boost = max(1.0, boost * decay)
```

```go
// go/ch16/sa_multi_neighborhood.go — 同じ boost / decay 切替
temperature := t0 * math.Pow(t1/t0, progress) * boost
decay := boostDecayFast
if sinceImprove > slowAfter {
	decay = boostDecaySlow
}
boost = math.Max(1.0, boost*decay)
```

| 状況 | boost の戻り方 | 意図 |
|---------|---|------|
| 改善が続いている | 速く 1 に戻る（速く冷える） | 良い谷を詰める |
| 停滞気味 | ゆっくり戻る | 熱いまま粘って谷を越える |

**魔理沙**: 土台が時間ベースなので、boost がいくら揺れても **終盤は必ず T1 付近まで冷える**。第9章の長所はそのまま残るぜ。

**霊夢**: 温度ログは stderr？

**魔理沙**: `sa step=... T=...` を出す。本番では **best と current と T** をセットで見ると調整が速い。

## 16.2 複数近傍の切り替え（Neighborhood Portfolio）

**霊夢**: 近傍って1種類じゃだめ？

**魔理沙**: 問題によって **効く操作が違う**。複数登録し、**改善に寄与した近傍に重み** を寄せる——ポートフォリオだ。

```python
neighborhoods = [
    ("change_day", neighbor_change_day),   # 1 日の種類を変更
    ("swap_days", neighbor_swap_days),     # 2 日をスワップ
]
weights = [1.0, 1.0]
wins = [0, 0]

idx = rng.choices(range(len(neighborhoods)), weights=weights, k=1)[0]
move = neighborhoods[idx][1](state, rng)        # 操作だけ受け取る
delta = move_delta(problem, state.types, move)  # 差分で Δ を計算（第9章 9.4）
if delta >= 0 or rng.random() < math.exp(delta / temperature):
    apply_move(state.types, move)
    score += delta
    if delta > 0:
        wins[idx] += 1  # 改善した操作だけ数える
```

**魔理沙**: `swap_days` の Δ は「a を b のタイプに変える」「b を a のタイプに変える」の **2 回の `delta_change`** で求まる。同じタイプ同士の入れ替えは Δ=0 で何も変わらないので、勝ちには数えない。

1000 ステップごとに `wins` から重みを更新:

```python
total = sum(wins) or 1
weights = [max(0.2, w / total * 2) for w in wins]
```

**霊夢**: 実際の AHC だとどんな近傍を混ぜるの？

**魔理沙**: 配置問題なら「1個動かす」「2個入れ替える」「回転する」、経路問題なら「2-opt」「1点挿し替え」など、**性質の違う局所操作** を混ぜるのが典型だ。第16章は Intro HC 互換の **日程スケジュール** で同じ骨格を示す。

## 16.3 再ヒート（Reheating）

**霊夢**: 冷え切ったら終わり？

**魔理沙**: **再ヒート** で温度を一時的に上げ、もう一度悪化受理を強くする。`STAGNANT_LIMIT` ステップ best が更新されなければ発火し、boost を `REHEAT_BOOST` に跳ね上げる。

```python
REHEAT_BOOST = 4.0
STAGNANT_LIMIT = 20000

if since_improve >= STAGNANT_LIMIT:
    boost = REHEAT_BOOST  # その時点の基準温度の 4 倍から、また 1 倍へ戻っていく
    since_improve = 0
    reheats += 1
```

```
スコア
  ^     /\      reheat後また揺れる
  |    /  \___/\
  |   /        \___
  +------------------→ 時間
```

**霊夢**: 無限に reheat したら？

**魔理沙**: **時間制限** で打ち切る。`TIME_LIMIT_SEC = 1.5` のように `time.perf_counter()` でループを切るのが本番作法（第9章・第11章と同じ）。

### 受理判定のおさらい（第9章との接続）

```python
accepted = delta >= 0 or rng.random() < math.exp(delta / temperature)
```

再ヒート後は **T が大きい** ため、しばらく悪化も通りやすい。`since_improve` は **best が更新されたときだけ 0** にリセットするのが第16章の実装だ。

| ログ | 読み方 |
|------|--------|
| `score=` | 現在解（悪化していることもある） |
| `best=` | 提出候補（歴代最高） |
| `boost=` | 温度の倍率（再ヒート直後は大きい） |
| `reheats=` | ここまでの再ヒート回数 |
| `wins=` | 近傍ごとの改善回数（`[change_day, swap_days]`） |

## 16.4 終盤の決め技（Large Neighborhood Search の入門）

**霊夢**: LNS って第19章じゃないの？

**魔理沙**: **入門** としてここで触れる。**広い近傍**＝解の一部を大きく壊して、残りを貪欲や短い SA で直す。第16章の `swap_days` は2日だけだが、終盤に **連続10日をランダム再生成** する近傍を1つ足すと LNS の味がする。

| 近傍の規模 | 例 | コスト |
|-----------|-----|--------|
| 小 | 1 日変更 | 低 |
| 中 | 2 日スワップ | 低 |
| 大（LNS 風） | 連続区間を再構築 | 高・強力 |

**霊夢**: 終盤だけ大近傍？

**魔理沙**: よくある。**残り時間 < 20%** のときだけ LNS 的近傍を混ぜる。青色の第19章で Destroy & Repair を本格化する。

## 16.5 ハンズオン: Intro HC 型スケジュールで複数近傍 SA

**霊夢**: 入力フォーマットは？

**魔理沙**: Intro HC 形式（`data/ch16/sample.txt`）。`days`・`decay`・`gain` 行列。第9章 `sa_template` と同じ `score_schedule`。

### Step 1: 実行

```bash
python python/ch16/sa_multi_neighborhood.py < data/ch16/sample.txt
go run go/ch16/sa_multi_neighborhood.go < data/ch16/sample.txt
```

stderr 例:

```
initial score=1025008
sa step=40239 score=1072916 best=1079455 T=2685.8 boost=1.00 reheats=0 wins=[5004, 581]
...
best score=1079507
```

（制限時間の 10% ごとに1行。step 数はマシン速度で変わる。）

**霊夢**: 第9章と best が同じなの。

**魔理沙**: D=5 の玩具だと、どちらも最適付近に届くからな。差が出るのは D=365 のような本番サイズだ。手元のランダム入力（D=365）で試すと、Go 版は第9章の約 170 万 → 約 181 万と伸びた。一方 Python 版は 1.5 秒で回せる手数が少なく、`swap_days` の分だけ1手が重くなって第9章より低かった。**近傍を足せば必ず伸びるわけではない**——手数とのトレードオフを計測で確かめるんだぜ。

stdout は最良スケジュール（各日 1〜26）。

### Step 2: 近傍の追加

```python
def neighbor_shuffle_block(state, rng):
    a, b = sorted(rng.sample(range(len(state.types)), 2))
    block = state.types[a:b]
    rng.shuffle(block)
    return ("block", a, block)  # 区間 [a, a+len(block)) を block に置き換える操作
```

`move_delta` と `apply_move` に `"block"` の分岐を足す。Δ は区間内の各日を **順に `delta_change` で変えて足し合わせ**、最後に元へ戻せば求まる。書いたら、ランダムな入力で `move_delta` と全再計算（`raw_score`）が一致することを確かめる。`neighborhoods` に登録し、`wins` の長さを3に合わせる。stderr の `wins=` で **どの近傍が伸ばしたか** を見る（16.6 演習）。

### Step 3: 冷却・再ヒートのチューニング

```python
STAGNANT_LIMIT = 5000   # reheat を早める
REHEAT_BOOST = 8.0      # reheat を強くする
BOOST_DECAY_SLOW = 0.99995  # 停滞時にもっと粘る
```

`reheat` の回数と **best 更新タイミング** をログに残す。

### Step 4: 配置問題への対応

| 第16章 | 配置問題に置き換えると |
|--------|---------------------------|
| `change_day` | 1 個の位置・向きを変える |

上位解法の解説では、SA の近傍を **複数用意して比率を調整** する話が頻出だ。緑色帯の第9章 SA をそのまま伸ばす章だ。
